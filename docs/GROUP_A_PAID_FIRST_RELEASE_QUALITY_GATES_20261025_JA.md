# グループA＋深夜監査室有料版｜有料販売優先・品質ゲート
更新: 2026-10-25 / 対象: 9製品 / 開発者用（購入者UIには掲載しない）

## 0. 今回確定した商品方針
- **9製品とも原則は買い切り有料商品を目標**とする。既存の「低価格版」は「無料版」を意味しない。
- **無料化は、QA完了後に、作品としての内容量・独自性が明確に軽量な場合だけ個別判断**する。機能不足やバグのあるものを無料として出荷する代替策にはしない。
- 実価格・割引・有料/無料の最終確定は、各製品の内容・市場比較・Partner Center設定を確認してから行う。現在は未確定。
- **最優先は実害のあるエラーゼロを証跡で確認すること**。その後、基本機能の完成度、初見の遊びやすさ、バランスと演出を確認する。
- 「機能が完璧」は無限の機能追加を意味しない。**購入者に約束する機能が欠落なく動作すること**を完成の定義とする。新機能を足して既存セーブを壊さない。
- Windows/MSIX/Store工程を通過してもゲーム内容の販売品質をPASS扱いしない。

## 1. リリースの停止条件（1件でも未達なら販売HOLD）
### P0 — 致命的な問題がないこと
1. 初回起動、主要アクション、異常入力、セーブ、アプリ再起動、更新、アンインストールでクラッシュ・データ消失・操作不能がない。
2. 機能の戻る/やり直す/キャンセル、失敗時の案内と復旧方法が成立する。購入者に開発用UI/URL/内部パス/QA_UNSIGNED/MSIXメッセージを表示しない。
3. データ・台帳の整合性とセーブ互換性が守られ、破損セーブは勝手に上書きしない。
4. ネットワーク接続を必要としない商品では、起動/ゲーム進行に外部サーバー依存がない。
5. ソース・Manifest・MSIX SHA/Identityの対応が記録され、署名/インストール/Store準拠を実物で確認する。

### P1 — 有料ゲームとしての機能完備
1. 「開始→主な判断→結果→進行/終了→保存/再開」の一巡が成立し、少なくとも序盤・中盤・終盤を通しプレイする。
2. 選択に意味があり、結果と理由がプレイヤーに理解できる。進行不能・必須の隠れ条件・不公平な乱数を回避する。
3. 操作説明が実際のUI/ルールに合い、既存機能や商品説明の約束と一致している。
4. 長期/複数周回、境界値、資金枯渇、空在庫、全員疲労、誤った保存ファイル等、タイトル固有の失敗経路を検証する。

### P2 — 販売UI・遊びやすさ
1. 初見で「何をする/何が起きた/次に何をする」が分かる。基本操作を常時優先表示し、詳細設定は必要な時だけ展開する。
2. 1024×768 と 1280×720で文字欠け・操作不能・重要ボタンの画面外配置がなく、マウス/キーボードを試す。
3. データは表だけにせず、状況に応じてゲージ・色・適切なアニメーション・結果比較を使う。見やすさと操作性を優先し、他作品の画像やUIを複製しない。
4. 初回説明だけでなく、失敗結果の理由、操作状態、セーブ済み表示、リセット確認と取り消し/バックアップ導線を提供する。
5. JP/EN表示を提供する製品は、操作に必要な動的文言・エラーメッセージも各言語で確認する。

**判定**: P0/P1の不足が1つでもあれば販売HOLD。P2に操作を妨げる欠陥があればP0としてHOLD。改善案の採否はゲーム品質と既存互換性で判断。

## 3. 既存のQA証拠と限界
- 2026-10-25の引継ぎ時点: SmallBusinessSimulator・finance-simulation・NightOfficeAuditor（12案件）は**ソース/一部UI・未署名MSIX候補**が作成済み。Store認定ではなく、P1/P2の総合販売合格でもない。
- UsedItemShopSimulator・FactoryInspectionSimulator・game-new・game-stadium・game は **GitHub Actionsのジョブ実行前停止（steps 0）**。コードのPASS/FAILを示さない。
- 上記5件には `scripts/run-unified-qa-windows.ps1` があり、UsedItemShopSimulatorには `scripts/run-all-five-private-qa.ps1` がある。Windows実行による証跡は未取得。
- Playwrightのタブ/スクリーンショットスモークは、主要ゲーム操作・セーブ・数十ターンの回帰を保証しない。**LOCAL_QA_HANDOFF.jsonのPASSだけでP0/P1が完了したと判断しない**。
- 有料版の24案件についてはソース/Windowsプレビューの成功報告あり。Store用MSIX、署名、WACK、実機の配布検証とは区別する。

## 4. 作業の順番（ゲート式）
1. 各作業ブランチのHEADと原本/保護ファイルを確認。main/release・公開設定・請求設定には触れない。
2. Runner失敗の5製品はWindowsで実QAを走らせ、ソース回帰＋実ブラウザ画面＋全主操作＋中断/保存/復元を**別々の証跡**として保存。
3. 既存MSIX候補3件と有料版を含め、上表の未完了機能を製品ごとに洗い出す。P0優先で小さく修正・テストを追加し、該当ブランチにコミット。
4. P0とP1を満たした製品から初見試遊・UI調整を行い、P2合格を確認。価格・無料化はこの後に個別判断。
5. 同一の確定ソースからMSIX/MSIXUPLOADを生成し、SHA-256、Manifest、実機インストール、起動、セーブ、更新/アンインストール、適用される認定前検査を記録。
6. Partner Centerの実値でStore ID/Identity/Publisher/PFN/Versionを照合し、コード担当の管理下で提出。Identity推測や別作品からの流用はしない。
7. 商品説明・価格・スクリーンショット・アイコン・素材権利/年齢区分等を確認し、販売可否を**9製品個別**に判断する。

## 5. 最終引き渡しに必要な最小の証跡
製品ごとにRepository URL / 作業ブランチ / 確定HEAD / ソーステスト件数・結果 / 本編通しプレイ結果 / UIスクリーンショット / セーブ・復帰のログ / QA停止事由 / パッケージ名とSHA-256 / Manifestと正式Identity照合 / Windowsインストール・更新QA / 未解決P0-P2 / 販売区分（有料/無料）と判断理由を残す。

**出荷不可の表示**: 未実施=NOT TESTED、環境停止=BLOCKED、コード失敗=FAIL、正式Identity不明=HOLD。推測でPASSにしない。

**操作分担**: GitHub作業ブランチのコード修正・CI・検証・引継ぎ資料は本チャット側で可能な範囲から進め、Windows実機の操作・Partner Center提出と価格確定はコード担当の管理下で実施する。作業ごとに実施/未実施を明記する。
